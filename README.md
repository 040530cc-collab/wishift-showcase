# 念造 · Wishift

**自然语言驱动的运行时创作与契约式 FPS 对战原型**

Wishift 是一个基于 Godot 的团队原型项目，将自然语言创作、可执行行为生成、版本恢复与第一人称对战结合。玩家在游戏内提出地图、武器、技能或交互机制的修改意图，由 AI 生成候选内容，经宿主验证后进入实际运行，再根据游玩反馈继续调整。

项目同时保留自由工坊与契约竞技两条路径：前者面向开放创作与快速试验，后者围绕公共规则、能力代价和对抗关系组织玩家的创作行为。

| 项目维度 | 说明 |
| --- | --- |
| 类型 | 游戏内创作工具与第一人称对战相结合的实验性原型 |
| 技术基础 | Godot、GDScript、JavaScript、Pi Agent Core、QuickJS-NG |
| 体验形式 | 自由工坊、契约占点、契约歼灭、单人机器人练习、局域网房间 |
| 开发方式 | 团队协作，结合 AI 辅助开发与实际运行验证 |
| 当前阶段 | 已有可运行原型，暂停迭代，尚未正式发行 |

## 1. 项目定位与设计问题

项目的核心设想是将内容创作嵌入游玩过程，使玩家可以在同一个环境中完成意图表达、内容生成、实际体验和修改反馈。当前原型重点处理三个相互关联的问题：

- **创作意图的可执行表达：** 将自然语言描述转化为结构化数据、行为程序及其调用条件，并接入引擎已有的场景、角色和交互接口。
- **开放能力的对抗约束：** 将能力效果与发动条件、使用代价、可见信息、干预窗口和公共房规共同组织，维持对局目标与反制空间。
- **运行过程的可恢复性：** 区分生成候选与已生效内容，在修改失败、请求取消、状态变化或程序异常后保留可继续工作的版本和会话。

上述方向共同构成“创作—验证—游玩—修订”的体验循环。当前创作能力依赖已开放的引擎接口，新增底层能力仍需要扩展宿主及其校验逻辑。

## 2. 玩法结构与体验循环

### 自由工坊：围绕当前作品的运行时编辑

玩家进入地图后，可通过自然语言调整场景对象、武器行为、角色表现和玩法逻辑。编辑请求绑定当前作品的身份与版本，生成结果进入独立候选流程，通过运行与渲染检查后再应用。版本树保留修改关系，支持查看差异、撤销与恢复。

地图创作与个人资源编辑具有不同的作用范围。地图内工坊可以操作当前作品的内容与行为；地图外的角色、武器编辑仅处理选中的资源数据，保存为相应的外观或收藏版本。将资源应用到具体地图时，仍须进入该地图完成适配。

### 契约竞技：公共规则下的能力创造

契约模式以明确的胜负目标组织创作。房主先公布比赛规则，玩家提出希望获得的能力，系统生成行为实现并协商使用条件。玩家阅读、确认并签订能力契约，房主再次检查后公示；全员准备完成后进入对局，赛间可对后续回合的规则进行修订。

| 模式 | 对抗目标 | 原型中的默认安排 |
| --- | --- | --- |
| 契约占点 | 围绕中央据点争夺控制权，单方控制时持续计分，双方进入时形成争夺 | 三分钟回合，先到目标分数获胜，支持复活规则配置 |
| 契约歼灭 | 通过团队配合使对方全队失去战斗能力 | 三分钟回合，默认不复活，超时按存活人数及生命值比较 |
| 单人练习 | 使用同一套比赛规则验证能力与对抗流程 | 可与三名练习机器人组成对局 |

基本对局流程为：

```text
公共房规与胜负目标
  → 能力意图与实现方案
  → 条件、代价和反制条款
  → 玩家确认与房主复核
  → 公示、准备及对局执行
  → 赛间讨论与下一轮修订
```

## 3. 能力契约与对抗约束

能力以可执行的行为程序表达，可以组合条件判断、时间序列、状态变化与实体操作。当前宿主提供位移、速度与重力、生命变化、状态、可破坏物体和公共信号等接口，生成程序在约定的观察与操作范围内运行。

契约同时描述“能力产生什么效果”以及“玩家为效果承担什么约束”。其主要组成如下：

| 组成 | 作用 |
| --- | --- |
| 行为实现 | 定义触发后的计算、时序、目标选择与效果组合 |
| 发动条件 | 限定能力成立时的角色状态、阶段或环境条件 |
| 操作权限 | 约束可影响的对象、范围、移动速度、伤害与实体数量 |
| 使用代价 | 由宿主执行扣血、禁火、位置暴露、次数限制或后续回合义务 |
| 反制窗口 | 通过公开蓄力、可摧毁核心、可见信号等方式提供干预机会 |
| 公示与确认 | 让参赛者在开始前了解当前能力及共同遵守的规则 |

行为程序与代价执行分开管理。房主维护权限、胜负和已成立的义务，能力代码只能提交效果意图；正式执行时，宿主继续检查目标、范围、视线、归属与付款条件。已成立的回合义务具有持续性，死亡、换约或重新连接不会自动清除。

规则变更会使原有准备状态失效，涉及模式、复活与能力政策的调整需要重新确认。赛间修订从后续回合生效，避免对已经结束的结果进行追溯改判。

## 4. 系统分层与执行边界

项目将游戏运行、模型编排、生成代码执行与持久化拆分为不同职责。

| 层次 | 主要职责 |
| --- | --- |
| Godot / GDScript 宿主 | 管理输入、页面状态、场景渲染、规则执行、数据校验与存档提交 |
| Pi Agent 编排 | 组织模型调用、按需读取、工具反馈、候选修复与原生会话恢复 |
| QuickJS-NG 执行环境 | 在隔离运行环境中执行生成的 JavaScript，并向宿主返回约定格式的数据或效果意图 |
| 契约房间与权威模拟 | 管理成员身份、能力公示、准备状态、胜负计算、代价执行与状态同步 |
| 版本与会话存储 | 保存作品修订、检查点、候选结果、模型消息与宿主应用回执 |

模型工具按照当前任务的范围开放：地图编辑可以发现、查询和修改当前作品；个人资源编辑只接收选中资源的数据结果；契约创作则使用能力程序与条款校验流程。不同入口复用模型与聊天基础设施，并分别保留各自的权限和提交约束。

Windows 端的生成代码通过原生隔离环境执行。模型等待、进程通信和候选验证使用后台处理，以降低这些工作对游戏主循环的影响。隔离执行、协议校验与宿主复核共同限制生成内容能够访问和影响的范围。

## 5. 内容生成、验证与生效流程

### 工坊内容

1. 根据当前作品身份、版本及修改意图，读取相关对象、属性或实现片段。
2. 生成带版本信息的候选补丁；必要时继续修复同一候选。
3. 在独立执行环境中初始化候选、重放输入并检查输出协议。
4. 由 Godot 进行实际渲染预览，核对候选与当前状态的一致性。
5. 持久化成功后安装已验证的候选，并记录对应版本与提交结果。

活动状态在生成期间仍可能变化，因此候选通过一次检查后，还需要在应用前核对状态与版本。请求取消、候选过期和保存失败沿各自的异常路径处理，避免把未完成的修改直接替换为正式内容。

### 契约能力

契约候选依次经过结构检查、隔离执行预检和独立上下文审查，随后由玩家阅读并确认。房主在装备阶段再次预检，同时核对当前房规与成员状态；正式对局中继续逐批校验效果意图及代价。

这些检查用于提高候选的可执行性和规则一致性。有限预检与 AI 审查仍无法覆盖任意程序的全部运行状态，也不能单独证明对战平衡；实际对局反馈和进一步测试仍是必要环节。

## 6. 会话持久化与版本一致性

作品版本与模型会话分别保存。作品存储负责内容修订、检查点、分支及恢复关系；原生会话保存模型交互与工具执行记录，界面的聊天摘要用于展示和选择会话。

修改请求关联当前作品版本，宿主回执记录候选是否已经实际应用，以及应用后的版本位置。会话重新打开时，系统需要恢复相应的消息与操作状态，并处理未完成请求，防止重复执行先前的内容修改。

历史恢复区分“请求尚未开始便失败”和“已有记录损坏”：前者可以保留用户意图与失败结果后继续请求，后者需要明确报错，避免静默丢失有效上下文。存储目录解析、同目录原子发布与会话身份保持也是 Windows 适配中的处理重点。

## 7. 联机同步与本地表现

契约房间采用房主权威方式推进规则与对局状态，通过局域网发现和可靠连接完成加入、准备及状态传输。加入端接收并表现房主状态；涉及能力装备和效果执行的关键判断由房主复核。

表现层与权威模拟采用分离的更新机制。相机可在收到的姿态间进行插值，本机房主或练习模式可结合待处理输入改善转向反馈，同时保留原有玩法模拟与联机同步节奏。该机制主要改善视角连续性，射击与胜负判定仍由模拟负责。

页面切换也需要保持运行状态的一致性：进入工坊、查看收藏、返回对局或离开房间时，界面可见性、输入捕获、创作目标与房间生命周期分别更新，避免隐藏页面继续占用输入或遮挡当前场景。

## 8. 个人参与与开发贡献

本人是 Wishift 的游戏创意贡献者之一，参与项目概念构思与原型开发。个人开发工作主要集中在 Windows 运行适配、功能调试、状态恢复与操作体验优化，并使用 AI 开发工具辅助实现和验证。

| 参与方向 | 工作内容 |
| --- | --- |
| 创意与原型 | 参与游戏概念构思及原型开发讨论，将实际运行反馈用于后续调整 |
| Windows 适配 | 整理本地启动流程与运行环境，处理平台相关的运行和存储问题 |
| 交互状态调试 | 排查模式切换、页面可见性与输入路由问题，完善进入和返回对局的流程 |
| 会话恢复 | 处理存储路径解析、异常请求记录及会话重开逻辑，保留有效历史并明确异常状态 |
| 操作体验 | 调整相机插值与更新机制，验证视角反馈、输入捕获及返回对局后的表现 |
| 验证与协作 | 补充相关回归检查，结合真实窗口和本地模型服务验证修改，通过 Git 分支整理和提交改动 |

本文中的整体玩法与系统结构属于团队共同开发成果；上表列出个人参与范围。

## 9. 验证范围与项目阶段

原型已开展的验证包括：

| 验证方向 | 覆盖内容 |
| --- | --- |
| 界面与输入 | 真实 Windows 窗口下的模式进入、场景显示、移动、转向及页面返回 |
| 模型与宿主协作 | 使用本地模拟模型服务验证真实进程通信、候选修复、应用与撤销 |
| 会话与存储 | 会话重开、有效历史保留、异常记录处理、目录解析与原子写入 |
| 视角表现 | 相机更新节奏、与权威姿态的一致性、切换后输入与相机状态 |
| 局域网逻辑 | 同机多进程的加入、动作、能力、状态同步与断线流程 |

现有成果包括可运行的契约占点与歼灭原型、机器人练习、最多四人的局域网房间逻辑，以及游戏内创作和版本恢复流程。跨设备与公网体验尚未完成验收，匹配、房主迁移及发行级平衡也仍需进一步工作。

项目当前暂停迭代，尚未正式发行。现阶段主要成果是玩法和运行流程的原型验证，内容规模、美术表现、长期稳定性与对战平衡仍有完善空间。
